# 卡片过程分组展示与拖拽修复设计

**日期：** 2026-08-19  
**状态：** 已批准（待用户确认书面 spec）  
**相关文档：** [todo-list-view-mode-design](2026-08-17-todo-list-view-mode-design.md)、[status-config-design](2026-07-07-status-config-design.md)  
**范围：** 卡片视图展示处置过程摘要；列表 API 附带过程摘要；修复代办列表与状态配置拖拽；状态配置增加上移/下移

---

## 1. 目标

卡片视图能看到代办下的处置过程：任意状态的过程均只显示**过程标题**与**过程状态**，并按过程状态分组。整卡最多展示 6 条过程；未完全展示的分组有「还有更多」标记。状态配置在保留拖拽的同时增加上移/下移；一并修复当前失效的代办列表拖拽与状态配置拖拽。

## 2. 需求摘要

| 项 | 决定 |
|----|------|
| 展示范围 | 仅卡片模式；列表行不展示过程 |
| 过程字段 | 仅标题 + 状态（不显示正文、时间、扩展字段、附件） |
| 分组依据 | 过程 `status`，组顺序 = 状态配置 `order` 升序 |
| 组内顺序 | `createdAt` 降序（新→旧） |
| 名额分配 | 按状态配置顺序占满全局最多 **6** 条（方案 A） |
| 未展全标记 | 分组末尾文案「还有更多」（无数字） |
| 0 可见但仍有过程的组 | 仍显示分组标题 +「还有更多」，组内无过程行 |
| 无过程 | 过程区显示「暂无过程」 |
| 数据方案 | 列表接口附带精简过程摘要（方案 1） |
| 截断位置 | **仅前端**；后端返回该工单下全部摘要 |
| 状态排序增强 | 保留拖拽 + 每行「上移 / 下移」 |
| 拖拽修复 | 代办列表（列表+卡片）与状态配置一并修复 |
| 回收站 | 不依赖过程摘要；仍仅列表、无卡片过程 |

## 3. 架构

### 3.1 数据模型

扩展 `WorkOrder`（Rust + TypeScript bindings）：

```ts
type ProgressLogSummary = {
  id: number | null;
  title: string;
  status: string;
  createdAt: string;
};

// WorkOrder 新增
progressSummaries: ProgressLogSummary[]; // 缺省实现为 []
```

- **不含** `content`、`extraFields`、附件信息。
- 主清单 `listWorkOrders` 路径必须填充；单条 `getWorkOrder` 可不填或填 `[]`（详情仍走 `listProgressLogs`）。
- 回收站列表可不填充摘要（填 `[]` 即可），因回收站无卡片过程展示。

### 3.2 后端

在 `find_by_statuses`（及主清单实际调用的列表查询）中，对结果集工单 id **批量**查询 `progress_log`：

- 字段：`id, work_order_id, title, status, created_at`
- 排序：`created_at DESC`
- 按 `work_order_id` 挂到对应 `WorkOrder.progress_summaries`
- 首版**不做**服务端条数截断；字段已精简，体量可控。若日后过程极多再加上限。

新建/更新/删除过程后，用户返回列表会重新拉取，自然刷新摘要；无需单独推送。

### 3.3 前端截断算法

纯函数（建议抽到 `utils` 或 composable，便于单测），输入：`summaries` + 按 `order` 排序的状态列表；输出：分组视图模型。

规则：

1. 仅对「至少有一条过程」的状态建组；状态顺序 = 配置 `order` 升序。配置中不存在的 `status`：排在已知状态之后，组标题走现有 `statusLabel` 兜底。
2. 组内按 `createdAt` 降序。
3. 按组顺序依次取过程行，全局计数，满 **6** 停止取行。
4. 若某组 `visibleCount < totalInGroup`：该组 `truncated = true`，末尾展示「还有更多」。
5. 若某组 `visibleCount === 0` 且 `totalInGroup > 0`：仍输出该组（仅标题 +「还有更多」）。
6. `summaries.length === 0`：不建组，UI 显示「暂无过程」。

### 3.4 文件改动预期

| 区域 | 改动 |
|------|------|
| Rust `WorkOrder` / progress 查询 / list 组装 | 摘要字段与批量填充 |
| specta / `bindings.ts` | 同步类型 |
| `WorkOrderList.vue` + `main.css` | 卡片过程区 |
| 截断工具函数 + 单测（若项目已有前端测）或后端测 | 分组/截断 |
| `StatusConfigPanel.vue` | 上移/下移；拖拽修复验收 |
| `tauri.conf.json`（若根因确认） | `dragDropEnabled: false` |
| 列表拖拽相关模板/样式 | 按根因修复 |

## 4. UI 行为

### 4.1 卡片结构（自上而下）

1. 标题（+ 拖拽把手 / 多选勾选，行为不变）
2. 标签（有则显示）
3. **过程区**（新增）
4. 元信息：代办状态、计划完成、最后更新（保留）

### 4.2 过程区

- 无过程：次要文案「暂无过程」。
- 有过程：按 §3.3 渲染分组。
  - 分组标题：状态显示名；可用紧凑状态色标签，与详情过程 header 语义一致。
  - 过程行：标题 + 状态小 tag。
  - 未展全：组末「还有更多」。
- 过程行不单独打开/编辑；点击冒泡到卡片 → 打开详情。
- 仅卡片模式展示；列表模式不变。

### 4.3 状态配置上移 / 下移

- 状态列表每行增加「上移」「下移」（text/tiny 即可）。
- 第一项禁用上移，最后一项禁用下移。
- `@click.stop`，避免误触发选中。
- 与拖拽共用 draft：交换后重写 `order` 为 `0…n-1`，仍经现有保存流程写入 `status_config.json`。
- 不新增后端 API。

### 4.4 拖拽修复

实现期先定位根因，优先验证：

- Tauri 2 默认 `dragDropEnabled: true` 与 HTML5 DnD / `vue-draggable-plus` 冲突 → 窗口配置设 `dragDropEnabled: false`。
- 附件现走选文件与粘贴，不依赖窗口级文件拖入；关闭后不削弱现有附件能力。
- 若仍失效：再查 handle、点击与拖拽冲突、覆盖层/CSS 等，直到：
  - 代办列表（列表 + 卡片）拖拽后 `reorder` 持久化成功；
  - 状态配置拖拽改序并写回 `order` 成功。

## 5. 错误与边界

- `progressSummaries` 缺失或 `[]`：过程区「暂无过程」。
- 过程状态不在配置中：仍建组，标题用现有 `statusLabel` 兜底。
- 列表加载失败：沿用现有错误提示；不因摘要单独静默丢整表。
- 拖拽 / `reorder` 失败：`message.error` 并刷新列表恢复顺序。
- 状态上移/下移仅改 draft；未点保存前不写盘（与现有编辑一致）。

## 6. 测试要点

- 后端：主清单工单含正确 `progressSummaries`；无 content；工单间不串数据。
- 截断：满 6 条停止；部分截断组有「还有更多」；0 可见组仍显示标题 + 标记；无过程文案。
- 组序：改状态 `order`（拖拽或上移/下移并保存）后，卡片分组顺序随之变化。
- 手工：Tauri 下代办列表与状态配置拖拽可用；上移/下移边界禁用正确。
- 回归：列表模式无过程区；回收站行为不变；卡片多选/右键/打开详情不变。

## 7. 非目标

- 列表行展示过程
- 卡片过程行内联编辑/删除
- 改详情「处置过程」时间线交互
- 回收站卡片或过程摘要依赖
- 恢复窗口级文件拖入附件
- 服务端截断过程条数（首版不做）
- 用户可配置「每卡最多 N 条」（固定 6）
